# คำอธิบายโมดูล (Module Specification) ฉบับปรับปรุง

เอกสารฉบับนี้ปรับคำอธิบายโมดูลให้ตรงกับการทำงานของโปรแกรมใน `webapp/` ปัจจุบัน โดยแยกให้ชัดเจนระหว่าง **เว็บแอปพลิเคชันสำหรับใช้งานโมเดล** กับ **กระบวนการฝึกและประเมินโมเดลที่ทำภายนอกเว็บแอปพลิเคชัน**

> ขอบเขตของเว็บแอปพลิเคชันคือการรับวิดีโอ ตรวจจับใบหน้า ใช้โมเดล Xception ที่เปิดใช้งานแบบ Ensemble แสดงผล และจัดการโมเดล/ประวัติในระบบ ส่วนไฟล์น้ำหนัก `.pth` ต้องผ่านการฝึกมาก่อนแล้วจึงนำมาอัปโหลดหรือวางไว้ใน `webapp/model/`

## 3.2.5.1 คำอธิบายกระบวนการตรวจสอบสิทธิ์

**ชื่อกระบวนการ:** ตรวจสอบสิทธิ์ผู้ดูแลระบบ  
**วัตถุประสงค์:** ตรวจสอบชื่อผู้ใช้และรหัสผ่านก่อนอนุญาตให้เข้าถึง API สำหรับผู้ดูแลระบบ  
**ข้อมูลเข้า:** `username`, `password`  
**ข้อมูลออก:** สถานะการเข้าสู่ระบบและ Session ของผู้ดูแลระบบ  
**ตารางข้อมูล:** `admins`

**ขั้นตอนการประมวลผล**

1. ผู้ใช้เปิดหน้า `/admin` ระบบแสดงหน้า Login
2. ผู้ใช้กรอกชื่อผู้ใช้และรหัสผ่าน โดยหน้าเว็บกำหนดให้กรอกข้อมูลที่จำเป็น
3. หน้าเว็บส่งคำร้องขอ `POST /api/admin/login`
4. ระบบค้นหาและตรวจสอบข้อมูลในตาราง `admins`
5. หากข้อมูลถูกต้อง ระบบกำหนด Session `admin_logged_in` และ `admin_user`
6. หากข้อมูลไม่ถูกต้อง ระบบส่งข้อความแจ้งเตือนและคงอยู่ที่หน้า Login
7. API สำหรับผู้ดูแลระบบตรวจสอบ Session ผ่าน `admin_required` ก่อนทำงาน
8. เมื่อผู้ดูแลกดออกจากระบบ ระบบเรียก `POST /api/admin/logout` และลบข้อมูล Session

## 3.2.5.2 คำอธิบายกระบวนการเพิ่มโมเดลที่ใช้ในการจำแนก

**ชื่อกระบวนการ:** เพิ่มโมเดลที่ใช้ในการจำแนก  
**วัตถุประสงค์:** นำเข้าไฟล์น้ำหนักโมเดล Xception และลงทะเบียนข้อมูลโมเดลในระบบ  
**ข้อมูลเข้า:** Model Key, ชื่อโมเดล, คำอธิบาย และไฟล์น้ำหนัก `.pth`  
**ข้อมูลออก:** รายการโมเดลใหม่ในตาราง `models` และไฟล์น้ำหนักใน `webapp/model/`  
**ตารางข้อมูล:** `models`

**ขั้นตอนการประมวลผล**

1. ผู้ดูแลเปิดหน้าต่างเพิ่มโมเดล
2. กรอก Model Key ชื่อโมเดล และคำอธิบาย พร้อมเลือกไฟล์โมเดล
3. หน้าเว็บตรวจสอบว่ามีไฟล์และนามสกุลเป็น `.pth`
4. ระบบส่งข้อมูลแบบ Multipart ไปยัง `POST /api/admin/models/upload`
5. Backend ตรวจสอบว่ามี Model Key และชื่อโมเดล
6. Backend ตรวจสอบนามสกุลไฟล์และสร้างชื่อไฟล์สำหรับจัดเก็บ
7. ระบบบันทึกไฟล์ลง `webapp/model/`
8. ระบบเพิ่มข้อมูลโมเดลลงตาราง `models` โดยกำหนดสถานะเริ่มต้นเป็น Active
9. หาก Model Key ซ้ำ ระบบยกเลิกการลงทะเบียนและลบไฟล์ที่เพิ่งอัปโหลด
10. ระบบส่งผลสำเร็จหรือข้อความผิดพลาดกลับไปแสดงแก่ผู้ดูแล

## 3.2.5.3 คำอธิบายกระบวนการลบโมเดลที่ใช้ในการจำแนก

**ชื่อกระบวนการ:** ลบโมเดลที่ใช้ในการจำแนก  
**วัตถุประสงค์:** ลบข้อมูลโมเดล ไฟล์น้ำหนัก และโมเดลที่ถูกเก็บไว้ในหน่วยความจำ  
**ข้อมูลเข้า:** Model Key ที่ต้องการลบ  
**ข้อมูลออก:** สถานะการลบโมเดล  
**ตารางข้อมูล:** `models`

**ขั้นตอนการประมวลผล**

1. ผู้ดูแลเลือกโมเดลและกดปุ่มลบ
2. ระบบแสดงหน้าต่างยืนยันการลบ
3. หากผู้ดูแลยกเลิก ระบบไม่ส่งคำร้องขอและจบกระบวนการ
4. หากยืนยัน ระบบส่ง `DELETE /api/admin/models/<key>`
5. Backend ค้นหาโมเดลจากตาราง `models`
6. หากไม่พบโมเดล ระบบส่งข้อความแจ้งเตือน
7. หากพบ ระบบลบรายการออกจากตาราง `models`
8. ระบบลบไฟล์น้ำหนักออกจาก `webapp/model/`
9. ระบบลบโมเดลรายการนั้นออกจาก Cache `MODELS`
10. ระบบส่งผลการลบกลับไปแสดงแก่ผู้ดูแล

## 3.2.5.4 คำอธิบายกระบวนการกำหนดสถานะการใช้งานโมเดล

**ชื่อกระบวนการ:** เปิดหรือปิดการใช้งานโมเดล  
**วัตถุประสงค์:** กำหนดว่าโมเดลใดสามารถถูกนำไปใช้วิเคราะห์วิดีโอ  
**ข้อมูลเข้า:** Model Key  
**ข้อมูลออก:** สถานะ `is_active` ใหม่ของโมเดล  
**ตารางข้อมูล:** `models`

**ขั้นตอนการประมวลผล**

1. ผู้ดูแลเลือกเปิดหรือปิดสถานะของโมเดล
2. หน้าเว็บส่ง `PATCH /api/admin/models/<key>/toggle`
3. Backend ค้นหาโมเดลจากตาราง `models`
4. หากไม่พบโมเดล ระบบส่งข้อความแจ้งเตือน
5. หากพบ ระบบสลับค่า `is_active` และบันทึกลงฐานข้อมูล
6. หากเปลี่ยนเป็น Inactive ระบบนำโมเดลออกจาก Cache `MODELS`
7. หากเปลี่ยนเป็น Active ระบบยังไม่โหลดทันที แต่จะโหลดแบบ On-demand เมื่อมีการวิเคราะห์
8. ระบบส่งสถานะใหม่กลับไปแสดงแก่ผู้ดูแล

## 3.2.5.5 คำอธิบายกระบวนการจำแนกวิดีโอดีปเฟก

**ชื่อกระบวนการ:** จำแนกวิดีโอดีปเฟก  
**วัตถุประสงค์:** วิเคราะห์วิดีโอด้วยโมเดล Xception ที่เปิดใช้งาน และสรุปเป็น Real หรือ Fake  
**ข้อมูลเข้า:** ไฟล์วิดีโอ และรายการโมเดลที่มีสถานะ Active  
**ข้อมูลออก:** Verdict, Confidence, Real/Fake Percentage, ผลแยกตามโมเดล และรายละเอียดวิดีโอ  
**ตารางข้อมูลที่เกี่ยวข้อง:** `models`

**ขั้นตอนการประมวลผล**

1. หน้าเว็บตรวจสอบไฟล์เบื้องต้นและส่ง `POST /api/analyze`
2. Backend บันทึกไฟล์วิดีโอชั่วคราว
3. ระบบเปิดวิดีโอและอ่านจำนวนเฟรม ความยาว อัตราเฟรม และความละเอียด
4. ระบบดึงรายการโมเดลที่มีสถานะ Active
5. หากไม่มีโมเดล Active ระบบยกเลิกและส่งข้อความแจ้งเตือน
6. ระบบโหลดโมเดลที่ยังไม่มีอยู่ใน Cache แบบ On-demand
7. ระบบเลือกเฟรมตามช่วงเวลาของวิดีโอ
8. ระบบแปลงเฟรมเป็น RGB และส่งเข้า MTCNN เพื่อสกัดใบหน้า
9. หาก MTCNN ไม่ได้ผล ระบบปัจจุบันใช้ Center Crop เป็นทางเลือกสำรอง
10. ระบบ Resize และ Normalize ภาพใบหน้า
11. ระบบส่งภาพเข้าโมเดล Active ทุกตัวและคำนวณ Softmax Probability
12. ระบบเฉลี่ยผลของโมเดลในแต่ละเฟรม และเฉลี่ยผลรวมตลอดวิดีโอ
13. ระบบสร้างผลลัพธ์แยกตามโมเดล พร้อม Verdict ของแต่ละโมเดล
14. ระบบสรุปผลรวมเป็น Real หรือ Fake ตามค่าความน่าจะเป็นของคลาส
15. ระบบส่งผลลัพธ์และรายละเอียดเฟรมกลับไปยัง Frontend

> ระบบปัจจุบันเป็น Binary Classification ระหว่าง Real และ Fake โดยใช้โมเดล Active หลายตัวแบบ Ensemble ไม่ได้จำแนกชนิด Deepfake เป็นคลาสแยกจากกัน

## 3.2.5.6 คำอธิบายกระบวนการแสดงผลการจำแนก

**ชื่อกระบวนการ:** แสดงผลการจำแนก  
**วัตถุประสงค์:** แสดงผลวิเคราะห์แก่ผู้ใช้และบันทึกประวัติการตรวจจับ  
**ข้อมูลเข้า:** ผลจำแนก รายละเอียดวิดีโอ ผลแยกตามโมเดล และข้อมูลเฟรม  
**ข้อมูลออก:** หน้าผลลัพธ์และรายการประวัติใน `detection_logs`

**ขั้นตอนการประมวลผล**

1. Frontend รับผลจาก `POST /api/analyze`
2. แสดง Verdict และ Confidence
3. แสดงผล Real/Fake แยกตามโมเดลที่ Active
4. แสดงความยาว ความละเอียด และจำนวนเฟรมที่วิเคราะห์
5. แสดงสถานะการประมวลผลเสร็จสิ้น
6. Backend บันทึกชื่อไฟล์ Verdict Confidence สัดส่วนผลลัพธ์ และข้อมูลวิดีโอลง `detection_logs`
7. ระบบลบไฟล์วิดีโอและ Thumbnail ชั่วคราวหลังการวิเคราะห์
8. Frontend แสดงผลลัพธ์ที่ได้รับ

> URL ของ Thumbnail ที่อยู่ในผลลัพธ์ปัจจุบันเป็นข้อมูลชั่วคราว เพราะไฟล์ถูกลบหลังจบการวิเคราะห์ และยังไม่ได้เก็บ Thumbnail ไว้ในประวัติถาวร

## 3.2.5.7 คำอธิบายกระบวนการแบ่งส่วนชุดข้อมูล

**สถานะในโปรแกรม:** ไม่ได้อยู่ในเว็บแอปพลิเคชันปัจจุบัน  
**วัตถุประสงค์:** เตรียมชุดข้อมูลสำหรับการฝึกโมเดล  
**ข้อมูลเข้า:** ภาพใบหน้าที่ติดป้ายกำกับ  
**ข้อมูลออก:** ชุดข้อมูลสำหรับ Train, Validation และ Test

กระบวนการนี้เป็นขั้นตอนเตรียมโมเดลภายนอกเว็บแอปพลิเคชัน ปัจจุบัน repository ไม่มีสคริปต์แบ่งชุดข้อมูลที่เรียกใช้งานโดย `server.py` ดังนั้นไฟล์โมเดลที่นำมาใช้ในเว็บต้องผ่านขั้นตอนนี้จากเครื่องมือภายนอกก่อน

## 3.2.5.8 คำอธิบายกระบวนการฝึกฝนโมเดล Xception

**สถานะในโปรแกรม:** ไม่ได้อยู่ในเว็บแอปพลิเคชันปัจจุบัน  
**วัตถุประสงค์:** ฝึกค่าน้ำหนัก Xception และสร้างไฟล์ `.pth` สำหรับนำเข้าเว็บแอปพลิเคชัน  
**ข้อมูลเข้า:** ชุดข้อมูลฝึก ชุด Validation และพารามิเตอร์การฝึก  
**ข้อมูลออก:** ไฟล์น้ำหนักโมเดล `.pth` และผลการฝึก

การฝึกโมเดลเป็นกระบวนการภายนอก เช่น Kaggle Notebook หรือสคริปต์ฝึกเฉพาะทาง เว็บแอปพลิเคชันไม่มี Endpoint หรือหน้าจอสำหรับเริ่มการฝึกโมเดล โดย `package_models.py` มีหน้าที่จัดแพ็กเกจไฟล์โมเดลเท่านั้น

## 3.2.5.9 คำอธิบายกระบวนการทดสอบโมเดล

**สถานะในโปรแกรม:** ไม่ได้อยู่ในเว็บแอปพลิเคชันปัจจุบัน  
**วัตถุประสงค์:** ประเมินโมเดลด้วยชุด Test ก่อนนำไฟล์ `.pth` มาใช้งานจริง  
**ข้อมูลเข้า:** โมเดลที่ผ่านการฝึก และชุด Test  
**ข้อมูลออก:** Confusion Matrix และค่าประเมินประสิทธิภาพ

กระบวนการทดสอบโมเดลต้องทำภายนอกระบบเว็บ ปัจจุบัน `server.py` ทำ Inference กับวิดีโอที่ผู้ใช้อัปโหลด แต่ไม่ได้เปรียบเทียบกับ Label จริง จึงไม่สามารถคำนวณ Confusion Matrix หรือค่าประเมินจากการใช้งานหน้าเว็บได้

## 3.2.5.10 คำอธิบายกระบวนการแสดงสถิติภาพรวม

**ชื่อกระบวนการ:** แสดงสถิติภาพรวม  
**วัตถุประสงค์:** แสดงภาพรวมการใช้งานระบบแก่ผู้ดูแล  
**ข้อมูลเข้า:** คำร้องขอสถิติจากผู้ดูแลที่ผ่านการตรวจสอบสิทธิ์  
**ข้อมูลออก:** การ์ดสถิติ Donut Chart และ Bar Chart  
**ตารางข้อมูล:** `detection_logs`, `models`

**ขั้นตอนการประมวลผล**

1. Frontend ตรวจสอบ Session ผ่าน `GET /api/admin/check`
2. หากยังไม่ได้เข้าสู่ระบบ ให้แสดงหน้า Login
3. หากเข้าสู่ระบบแล้ว เรียก `GET /api/admin/stats`
4. Backend ดึงข้อมูลจาก `detection_logs`
5. คำนวณจำนวนวิดีโอ Real/Fake และสัดส่วนผลลัพธ์
6. ดึงจำนวนโมเดลที่ Active
7. คำนวณแนวโน้มการใช้งานรายวัน
8. Frontend แสดงการ์ดสรุป Donut Chart และ Bar Chart

> ระบบปัจจุบันยังไม่ได้คำนวณหรือแสดงค่าเฉลี่ย Confidence ตามที่ระบุไว้ในคำอธิบายเดิม

## 3.2.5.11 คำอธิบายกระบวนการแสดงประวัติการตรวจจับ

**ชื่อกระบวนการ:** แสดงประวัติการตรวจจับ  
**วัตถุประสงค์:** ดึงและแสดงรายการตรวจจับย้อนหลังแก่ผู้ดูแล  
**ข้อมูลเข้า:** Session และพารามิเตอร์ `limit`  
**ข้อมูลออก:** ตารางประวัติการตรวจจับ  
**ตารางข้อมูล:** `detection_logs`

**ขั้นตอนการประมวลผล**

1. Frontend เรียก `GET /api/admin/history`
2. Backend ตรวจสอบ Session ผ่าน `admin_required`
3. Backend ดึงรายการจาก `detection_logs`
4. เรียงข้อมูลตามรายการล่าสุดก่อน
5. ส่งชื่อไฟล์ Verdict Confidence Real/Fake Percentage ความยาว ความละเอียด และวันเวลา
6. Frontend แสดงข้อมูลเป็นตาราง

> ระบบปัจจุบันยังไม่มีช่องค้นหา ตัวกรองสถานะ และ Pagination แบบที่ระบุไว้ในเอกสารเดิม โดยใช้การจำกัดจำนวนรายการแทน

## 3.2.5.12 คำอธิบายกระบวนการตรวจจับและสกัดใบหน้าด้วย MTCNN

**ชื่อกระบวนการ:** ตรวจจับและสกัดใบหน้าด้วย MTCNN  
**วัตถุประสงค์:** แปลงเฟรมวิดีโอเป็นภาพใบหน้าสำหรับโมเดล Xception  
**ข้อมูลเข้า:** เฟรมภาพแบบ BGR จาก OpenCV  
**ข้อมูลออก:** ภาพใบหน้าขนาดที่โมเดลรองรับ

**ขั้นตอนการประมวลผล**

1. แปลงเฟรมจาก BGR เป็น RGB
2. แปลงเป็น PIL Image
3. ส่งภาพเข้า MTCNN ซึ่งทำหน้าที่ตรวจจับและจัดแนวใบหน้า
4. หากตรวจพบใบหน้า ระบบรับผลภาพใบหน้าที่ผ่านการ Crop และ Margin
5. หาก MTCNN ไม่คืนผลลัพธ์หรือเกิดข้อผิดพลาด ระบบปัจจุบันใช้ Center Crop
6. ส่งภาพกลับไปยังขั้นตอน Transform และ Inference

> โค้ดเรียกใช้ MTCNN เป็นโมดูลสำเร็จรูป จึงไม่ได้ดึง Bounding Box หรือ Facial Landmarks มาแสดงในผลลัพธ์โดยตรง

## 3.2.5.13 คำอธิบายกระบวนการ Xception และ Depthwise Separable Convolution

**ชื่อกระบวนการ:** Xception Feature Extraction  
**วัตถุประสงค์:** สกัดคุณลักษณะภาพใบหน้าเพื่อใช้จำแนก Real/Fake  
**ข้อมูลเข้า:** Tensor ภาพใบหน้าที่ผ่าน Transform  
**ข้อมูลออก:** Logits ของคลาส Real และ Fake

1. ระบบสร้างโมเดล `legacy_xception` ผ่าน `timm`
2. ภาพถูกส่งผ่าน Entry Flow, Middle Flow และ Exit Flow ของ Xception
3. สถาปัตยกรรมภายในใช้ Depthwise Separable Convolution ตาม Backbone
4. Global Pooling และ Classifier สร้างค่า Logits
5. โมเดลถูกย้ายไปยัง CPU หรือ CUDA ตามอุปกรณ์ที่มี
6. โมเดลอยู่ในโหมด Evaluation และใช้ `torch.no_grad()` ระหว่าง Inference

## 3.2.5.14 คำอธิบายกระบวนการ Transform และ Activation ภายในโมเดล

ก่อนเข้า Xception ระบบทำ Transform ดังนี้:

1. Resize ภาพใบหน้าให้เป็นขนาดที่โมเดลรองรับ
2. แปลงภาพเป็น Tensor
3. Normalize ด้วยค่า Mean และ Standard Deviation ของ ImageNet
4. เพิ่มมิติ Batch และส่งไปยังอุปกรณ์ประมวลผล

ส่วน Activation และ ReLU อยู่ภายใน Backbone ของ Xception ที่สร้างจาก `timm` ไม่ได้ถูกเรียกเป็นฟังก์ชันแยกใน `server.py`

## 3.2.5.15 คำอธิบายกระบวนการ Global Average Pooling

**ชื่อกระบวนการ:** Global Average Pooling  
**วัตถุประสงค์:** ลด Feature Map ให้เป็นเวกเตอร์คุณลักษณะก่อนเข้า Classifier

1. Feature Map จาก Exit Flow ถูกส่งเข้า Global Pooling ภายใน Xception
2. ระบบรวมข้อมูลเชิงพื้นที่ของแต่ละ Channel
3. ได้เวกเตอร์คุณลักษณะสำหรับชั้น Classifier
4. ขั้นตอนนี้ทำงานอยู่ภายในโมเดล `legacy_xception` ของ `timm`

## 3.2.5.16 คำอธิบายกระบวนการ Fully Connected Classifier

**ชื่อกระบวนการ:** Fully Connected Classifier  
**วัตถุประสงค์:** แปลงเวกเตอร์คุณลักษณะเป็น Logits ของสองคลาส

1. รับเวกเตอร์คุณลักษณะจาก Global Pooling
2. ส่งผ่าน Classifier ของ Xception
3. กรณี Checkpoint เป็นรูปแบบ `backbone.*` ระบบใช้ Dropout และ Linear Layer ที่กำหนดใน `XceptionDeepfakeClassifier`
4. กรณี Checkpoint เป็น State Dict ของ `timm` ระบบสร้าง `legacy_xception` ที่มีจำนวนคลาสเป็นสอง
5. ส่งค่า Logits ไปยัง Softmax ในขั้นตอน Inference

## 3.2.5.17 คำอธิบายกระบวนการ Softmax และการตัดสินผล

**ชื่อกระบวนการ:** Softmax และ Binary Decision  
**วัตถุประสงค์:** แปลง Logits เป็นความน่าจะเป็นและสรุปผล Real/Fake

1. ระบบรับ Logits จากโมเดล
2. คำนวณ `torch.softmax(outputs, dim=1)`
3. อ่านค่าความน่าจะเป็นของคลาส Real และ Fake
4. ระบบเฉลี่ย Probability จากโมเดล Active และเฟรมที่วิเคราะห์
5. หากค่าของ Fake มากกว่าค่ากึ่งกลาง ระบบสรุปเป็น Deepfake
6. หากไม่มากกว่า ระบบสรุปเป็น Real
7. Confidence เท่ากับ Probability ของคลาสที่ถูกเลือก
8. ระบบจัดทำผลรวมและผลแยกตามโมเดลส่งกลับไปยัง Frontend

> การทำงานปัจจุบันเป็น Binary Decision แบบ Real/Fake ไม่ใช่ Argmax สำหรับคลาส Deepfake หลายประเภท
